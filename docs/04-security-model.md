# 04 — Security Model

Status: Proposed · Applies to receiver + companion protocol. The phone connection is **untrusted network input** until pairing completes.

## 1. Threat model

| Adversary | Capability | Goal | Countermeasures |
|---|---|---|---|
| Rogue LAN peer (e.g., compromised IoT on same hotspot) | scan, connect, spoof mDNS, replay, flood | pair silently / crash / spy | PAKE pairing code; cert pinning; rate-limited listener; bounded parsers |
| MITM during first pairing | intercept traffic | steal session / downgrade | TLS 1.3 always-on from first byte; fingerprint shown in QR + UI comparison |
| Malicious "phone" app after pairing | send crafted streams/metadata | memory corruption via decoder, resource exhaustion | strict caps negotiation (max res/fps/bitrate), GStreamer caps filters before decode, packet size/seq validation, single-session limit |
| Compromised receiver config file | attacker-writable config | point listener anywhere / disable checks | config schema validated; secrets stored with user-only perms (`0600`); no exec of external commands — ever |

Out of scope v1: physical attacks, compromised OS on either side, DRM-protected content capture.

## 2. Cryptographic design

* **Identity:** receiver generates ECDSA P-256 self-signed cert at first run (rcgen); fingerprint = SHA-256. Phone generates keypair in Android Keystore at install.
* **Transport:** TLS 1.3 (rustls server-side; Kotlin `SSLSocket` client-side). No plaintext mode exists — not even "diagnostic" one.
* **Pairing:** 6-digit random code displayed on both screens, valid 120 s, single use; SPAKE2 proof exchanged over the already-TLS channel → protects against QR-less LAN attackers even if a user skips comparing fingerprints. **Implemented (Phase 2)**: `net::pairing` runs SPAKE2 inside the QUIC/TLS session; both sides derive HMAC-SHA256 confirmation keys; a fresh code is required per pairing window.
* **TOFU + reconnect tokens:** at pairing the receiver stores `{device_id, name, token}` in its data dir; reconnect presents the token via `Hello{auth_token}` and is silently accepted only on exact match — no token ⇒ full pairing flow required. Certificate fingerprint is shown in the UI for out-of-band comparison. **Media keys:** planned for Phase 3+ — fresh per session, generated by receiver, delivered over the authenticated control channel; media packets AEAD (AES-256-GCM) with sequence-derived nonces + 128-entry replay window when not using QUIC datagrams (QUIC path: TLS 1.3 handles everything).

No custom crypto primitives — only rustls/ring, SPAKE2 crate, javax.crypto.

## 3. Input validation rules (enforced in `wd-protocol` + `net::MediaIngest`)

1. Every parser is total: malformed input ⇒ typed error, never panic; fuzz targets cover all message codecs and the RTP ingest path (cargo-fuzz, Phase 6+).
2. Hard limits negotiated in `SessionAnswer`: width ≤ 3840, height ≤ 2160, fps ≤ 60, video bitrate ≤ 25 Mbps, audio ≤ 320 kbps; H.264 profile ≤ High; SPS values outside caps ⇒ stream rejected.
3. RTP: SSRC must match session answer; seq within replay window; payload length ≤ 1400 B; unknown payload types dropped + counted.
4. Control messages ≤ 4 KiB; unknown types ignored (versioning), known-but-invalid rejected.
5. Device names / any metadata are plain text, length-capped (64 B), rendered as text only.
6. Listener accepts exactly one active session; additional connections refused politely.
7. Timeouts: handshake 5 s, pairing 120 s, media silence 5 s, RTT watchdog 2 s.

## 4. Resource & privacy guarantees

* No telemetry, no internet requirement, no outbound connections except to paired phone.
* Logs contain IPs and metrics, never captured frame content or audio.
* Secrets (pinned certs, identity keys) under XDG data dir, `0600`.
* Memory safety: safe Rust everywhere; `unsafe` forbidden outside `-sys` crates (none planned).
